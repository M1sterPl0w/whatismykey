# Design

## Context

The pure logic (`notes`, `chord`, `key`, `scales`) exists and is tested, with no DOM code. `src/main.ts` is a placeholder and `index.html` has an empty `#app` div. The look was picked from mockups: light "Paper" style, with the "Stage" colours as dark mode. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- A small app that stays easy to read and change, with all music decisions left to the existing modules.
- State in one place, with the screen redrawn from it after every change.
- Light and dark themes from CSS variables, so a colour change is a one-line edit.

**Non-Goals:**
- Microphone input, saved songs, a manual theme switch, and offline install (PWA). The PWA comes in its own change.
- Any UI framework.

## Decisions

- **Plain TypeScript, no framework.** The screen has one list, a few button rows and one drawing. A render function per area, called from one `render()`, is enough. Alternative: Svelte or React. Rejected, because it adds a dependency and build complexity for a screen this small.
- **One state object:** `{ chords: Chord[], capo: number, pendingRoot, pendingQuality, selectedKey, selectedScale }`. Every tap updates the state and calls `render()`. Detection runs inside `render()`; it is cheap.
- **Derived data is not stored.** Sounding chords, detection result and scales are computed from state each time, so they cannot go stale.
- **Fretboard as inline SVG** generated by a pure function `fretboardSvg(notes, root)` that returns a string. It uses `viewBox` so it scales to the phone width. Alternative: canvas. Rejected, because SVG stays sharp and styles with CSS variables.
- **Theming by CSS variables** on `:root`, overridden in `@media (prefers-color-scheme: dark)`. No JavaScript is needed for theming.
- **Pure view helpers are unit tested** (fretboard marks, chord list text, key labels). DOM wiring is checked by running the app, because the repo has no browser test setup.
- **Layout:** one column. Top to bottom: chord list and capo, root buttons, quality buttons, key results, scale chips, note names, fretboard.

## Risks / Trade-offs

- [12 frets on a 360 px screen make small labels] → Use 7 px labels at that width and keep dots at least 12 px wide; check on a real phone and enlarge if unreadable.
- [Two rows of 12 root buttons are tall] → Lay the roots out in 2 rows of 6 so every button stays at least 40 px.
- [DOM wiring has no automated test] → Keep the wiring thin and move logic into tested helper functions.
